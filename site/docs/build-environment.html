Written 28 August 2026. Two decisions that sit underneath Projector-Build-Plan.md and explain its numbers: what the build happens in, and how the design language survives contact with generated code.

The decision: a git repository, not Lovable

The 27 August sprint plan already contained the argument without acting on it. It said the engineer has to build the realtime spine "because the session clock and the note-firing engine are the parts Lovable produces convincingly and wrongly." That is a statement about a ceiling.

Confidently wrong is the worst output available on this build, and there is a worked example in this vault from the day before. Ruskin's bin/build.mjs threw a ReferenceError on its first LARB article, printed the stack trace, and exited 0. Nothing flagged it. The feed would have gone stale in silence. It was caught because the output was checked rather than the exit code, and the fix is now a guard in the publish path that requires feed.json to be newer than it was and to parse with a non-empty books array. Neither the guard nor the catch is available inside a hosted prompt-to-app builder: there is no test runner to hold it and no diff to read.

Three other things follow from a repository, in descending order of how much they matter.

The engineer inherits an ordinary codebase. No generated React to correct, no eject moment between the beta and whatever comes after. His brief used to warn him to expect to correct the front end rather than admire it. That warning is gone.

The design system can live as code. See below; this is the larger of the two design points.

There is a real history. Every change is a diff someone can read, which is the only mechanism that catches the class of bug above.

The evidence that the mode works for this project is already in the folder: projector/wireframes/ is thirteen hand-built artboards with a real token sheet, produced this way.

Conductor as the shell, and its honest limits

Conductor is a Mac app from Melty Labs that runs Claude Code, Codex and Cursor agents in parallel, each in its own git worktree with its own branch, terminal and diff, then walks through review, pull request and merge. Free with an existing Claude or Codex subscription. Pro at $50 a month adds cloud workspaces, multiplayer to five people, an API and a mobile app.

Its marginal value over plain Claude Code with git worktrees is the interface, for running three or four lanes at once and reviewing their diffs side by side. That is worth less at 35 hours of work than it would be at a hundred. It is free, the download is small, and the failure mode is an hour lost and a return to the Ruskin workflow.

So the decision that actually matters is Lovable versus a repository, and Ruskin already answered it. Conductor is one comfortable wrapper on the answer, not the answer.

The bounded risk in either case is review throughput. The value of running four agents at once is capped by the ability to judge what four agents produced, and four lanes producing code nobody reads is worse than one Lovable app that can at least be seen. Not every line needs reading. Running the app after each merge does, and so does noticing when a diff is doing something it should not.

A one-day spike settles the Conductor question, which is the only one still open here. Build the note editor screen against the existing spec, including manual mm:ss and the still upload, in Conductor rather than in plain Claude Code with git worktrees. If the lanes are worth the interface and the diffs are legible side by side, keep it. If setup eats the day, drop it and use worktrees directly. One day out of twelve weeks either way, and nothing about the repository decision depends on the answer.

The design language: the problem is real in general and solved here in particular

The general worry is correct. A coding agent handed a prose prompt produces the house style everyone recognises, and no quantity of "make it premium" fixes it.

It does not apply to this build, because the invention has already happened. projector/wireframes/_kit.txt is a complete design system expressed as code: Archivo at 125% width for the marquee, Hanken Grotesk, JetBrains Mono with tabular numerals, Source Serif 4 for the curator's voice; oklch tokens for both lighting states; component classes down to .livedot's two-layer glow and the .desk chrome that fakes a browser bar. Section 8 of the product spec supplies the rules and, more usefully, the don'ts: no silver on resting surfaces, no serif in chat, oxblood exactly twice.

So the design language pass is a compile step, not a creative one. Lift _kit.txt into the application stylesheet as the single source of truth and build every screen against those tokens. The two lighting states, the serif as the curator's voice and nowhere else, and the chat rule are then enforced by the tokens rather than requested in a prompt. This is why the build plan prices that pass at two to three hours rather than six to ten, and it is the strongest single reason the numbers moved.

The thing that is actually missing: the agent cannot see

An agent writes CSS and never looks at the result, which is how the tenth screen drifts from the first.

Install Playwright MCP and close the loop: change, navigate, screenshot, compare against the artboard, iterate. That one addition is the difference between guessing at spacing and being able to tell that a note is holding six seconds rather than seven. Two skills wrap the workflow if it should be enforced rather than remembered, Visual Review for screenshot-and-evaluate and Eyes for a capture, propose, confirm and verify cycle, but the MCP server is the part that matters. It belongs in the engineer's first three days, before any screen exists.

Second, and free: the thirteen artboards in projector/wireframes/ are pixel references. Pointing an agent at the artboard and the screenshot together and asking what differs is a far sharper instruction than any adjective.

Which installed skills to use, and which to keep away from this

Already installed and worth running here:

  • impeccable-craft for building a screen end to end against the tokens.
  • critique and audit against each finished screen. Audit catches the contrast failure in --dim on --night before a curator does.
  • ui-build-quality for the states nothing else writes: an empty note queue, a failed upload, a dropped connection. These overlap the engineer's failure-states deliverable and are where a build stops looking like a demo.

Keep away from this project: frontend-design, high-end-visual-design, design-taste-frontend, gpt-taste, minimalist-ui, industrial-brutalist-ui. Every one of them exists to make an agent commit to an aesthetic. The aesthetic was committed to in August. Running them now is how the serif ends up in chat.

Outside references rather than installs: awesome-claude-design is a curated collection whose Cinematic Dark and Cult/Indie families, the latter listing Criterion and A24 explicitly, are the nearest published analogues to what already exists here, useful as a check rather than a replacement. Claude-Code-Frontend-Design-Toolkit is the best single index of what is available. Ignore the star counts quoted in write-ups about either; several looked inflated and none were verified.

Where an agent should not be doing the work at all

Net-new visual invention. A screen that is not among the thirteen artboards should be drawn as an artboard first, in the Claude canvas the wireframes came from, and only then built against the picture. That discipline already exists in the spec, which records the canvas URL and the tools/build-wireframes.py step that stops the pages and the canvas drifting apart. Kept, it means an agent is only ever implementing a design, which is the thing it is reliably good at.
